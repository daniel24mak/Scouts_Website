# Finance and Storage Workspaces Design

## Purpose

Extend the existing St. Mary's Scouts Dubai dashboard into one shared application with focused Scouting, Finance, Storage, Media, and Administration workspaces. Finance and Storage become complete operational workspaces without changing existing accounts, public routes, Scouting workflows, or legacy role behavior.

The governing model is: one account, multiple roles, multiple workspaces, one shared dashboard shell.

## Current-State Findings

- React 18, Vite, React Router `HashRouter`, and Supabase are already established.
- The protected dashboard is currently a single `/dashboard` route rendered by `AdminDashboardPage.jsx`.
- Dashboard navigation is state-based through `activeSection`, not URL-based.
- `AdminDashboardPage.jsx` owns the shell and many unrelated feature renderers, so Finance and Storage must live in dedicated feature modules.
- The dashboard bootstrap loads most existing modules together. Finance and Storage data must be route-scoped and lazy.
- The normalized access-control foundation already supports roles, permissions, global/group/team/event/own-record scopes, assignment expiry, direct denies, MFA requirements, and server-calculated effective access.
- Finance and Storage teams and preliminary roles exist, but neither domain has operational tables or UI.
- Existing approval flows are feature-specific. Finance and Storage require a shared server-enforced approval engine.
- Existing audit logs and notifications can be extended, but task aggregation and workspace deep links need a normalized contract.
- Existing People & Access work is uncommitted and must remain intact.

## Workspace Architecture

### URL model

The dashboard supports these canonical routes:

- `/dashboard/scouting`
- `/dashboard/finance`
- `/dashboard/storage`
- `/dashboard/media`
- `/dashboard/admin`
- `/dashboard/my-work`

Workspace pages use nested module paths, for example `/dashboard/finance/reimbursements` and `/dashboard/storage/inventory`. The legacy `/dashboard` URL resolves to the best permitted workspace. Existing legacy redirects continue working.

### Workspace registry

A centralized registry defines each workspace's key, name, icon, description, access permission, default route, navigation, mobile navigation, quick actions, and badge provider. Components must not scatter role-name checks to decide workspace visibility.

Workspace selection changes presentation only. Every query and mutation remains protected by effective permissions, RLS, trusted SQL functions, or Edge Functions.

### Access resolution

Available workspaces are derived from current server-calculated effective permissions. The resolver validates, in order:

1. Last-used workspace.
2. Preferred workspace.
3. Primary workspace.
4. First permitted workspace.

Saved local state is never authoritative. A removed or expired permission causes an automatic valid fallback. The last valid module is stored independently for each workspace and revalidated before restoration.

### Existing dashboard compatibility

The current dashboard remains the initial Scouting and Administration implementation. Its existing section IDs and workflows remain valid while URL synchronization and workspace filtering are added around them. Finance and Storage use dedicated feature directories, services, styles, and route-level loaders.

## Shared Shell

The existing top bar, sidebar, mobile bottom navigation, notifications, profile, theme, search, loading states, and error handling remain shared.

The shared shell adds:

- A workspace switcher for users with multiple workspaces.
- Current workspace identity on mobile.
- Workspace-specific navigation generated by the registry.
- Global My Work access.
- Permission-aware deep-link handling.
- Unsaved-change confirmation before workspace changes.

Users with one workspace enter it directly and do not receive a redundant selector.

## Global My Work

Each domain exposes a task provider returning a normalized task shape:

- ID and workspace key.
- Title and task type.
- Urgency, status, and due date.
- Related group, team, event, account, request, or person.
- Required permission and scope.
- Canonical deep link.

The global page combines permitted tasks without loading complete ledgers or inventories. Opening a task revalidates access, changes workspace, and opens the exact record.

## Authorization Model

Workspace access permissions are added for Scouting, Finance, Storage, Media, and Administration. Workspace access does not imply module or mutation access.

Finance and Storage receive granular permissions matching the approved specification. Built-in roles receive explicit permission bundles; team membership alone grants no authority. Direct denies continue to override role grants. High-risk permissions can require AAL2.

Authorization enforcement occurs in four layers:

1. Route and navigation guards for user guidance.
2. Service-level permission and scope validation.
3. RLS and trusted SQL/RPC functions for data access.
4. Edge Functions for privileged, multi-record, or sensitive-file operations.

## Shared Approval Engine

Finance and Storage use one normalized approval engine with:

- Workflow templates and versions.
- Ordered and parallel stages.
- Named, role, team, group, and event approvers.
- Conditional amount or resource rules.
- Pending, approved, rejected, and changes-requested outcomes.
- Comments, delegation, escalation, deadlines, and immutable history.
- Backend prevention of self-approval and other separation-of-duty conflicts.

Existing content and form approvals are not migrated until compatibility has been proven. The new engine initially serves Finance and Storage and exposes adapters for future migration.

## Finance Domain

### Core accounting

Finance uses double-entry accounting beneath simple user actions. Posted journal entries must balance. Only posted entries affect official balances. Posted entries are corrected through reversals or adjusting entries, never silent edits or deletion.

Core records include ledger accounts, operational accounts/cashboxes, funds, categories, journal entries, journal lines, source references, and accounting periods. Physical account location and allocation fund remain separate concepts.

### Workflows

Finance modules include overview, transactions, accounts and cashboxes, funds, budgets, purchase requests, reimbursements, income and collections, reconciliation, periods, reports, and settings.

Budgets are hierarchical and versioned. Commitments, pending requests, actual spending, remaining availability, forecast values, and thresholds are computed from authoritative records.

Purchase requests, reimbursements, collections, reconciliation, and period closing use server-enforced transitions and approval policies. Sensitive payment details are masked and never include full card data.

## Storage Domain

### Inventory truth

Storage supports consumables, reusable bulk stock, individually tracked assets, and kits. Availability is derived from immutable movement, reservation, issue, return, adjustment, damage, maintenance, and retirement records rather than one editable quantity.

### Workflows

Storage modules include overview, inventory, requests, reservations, loans and returns, kits, locations, restocking, suppliers and deliveries, maintenance, audits, reports, and settings.

Requests reserve stock only after validation. Handover and return records support partial quantities and condition inspection. Restricted areas, safety-critical assets, discrepancy approvals, maintenance, and write-offs are protected by granular permissions.

## Finance and Storage Integration

Cross-domain workflows use stable foreign keys and immutable source references:

- Restock request to purchase request, commitment, delivery, inventory movement, invoice, and expense.
- Damage or loss to estimate, approval, transaction, and repair or replacement record.
- Borrower charge to Finance charge, payment or waiver, and Storage case completion.
- Asset purchase transaction to asset record and purchase value.

Neither workspace may mutate the other workspace's authoritative decision fields without the corresponding permission.

## Files and Privacy

Finance receipts, statements, invoices, quotations, and payment proof are private. Storage condition photos, maintenance records, delivery notes, audits, and warranties are private unless explicitly classified otherwise.

Uploads use private buckets or scoped private paths, generated filenames, size/type limits, authorization checks, signed URLs, and metadata reduction where appropriate. Service-role credentials never enter frontend code.

## Audit and Notifications

Important domain actions write immutable audit events with actor, action, module, resource, safe before/after values, outcome, reason, timestamp, and request identifier. Secrets and complete banking details are excluded.

Notifications and My Work records deep-link to canonical workspace routes and are completed when their underlying work is resolved.

## Performance

- Route-level lazy loading for Finance and Storage.
- No Finance or Storage data in the general dashboard bootstrap.
- Server-side pagination, filtering, and summaries.
- Indexed permission, status, date, account, item, location, and source-reference queries.
- Database-calculated balances and availability.
- Cached reference catalogs and narrow task queries.

## Responsive and Accessible UI

The existing blue, white, and gold dashboard design system is reused. Workspace modules use feature-scoped CSS and shared form, card, table, status, modal, loading, and empty-state primitives.

Desktop uses compact internal workspace navigation. Tablet may use tabs or selectors. Mobile keeps no more than five primary bottom actions and moves secondary modules into a More sheet. All controls meet touch, keyboard, contrast, focus, screen-reader, safe-area, reduced-motion, and semantic-table requirements.

## Migration and Rollback

Migrations are additive, idempotent where practical, and split by responsibility. Existing data is not rewritten or deleted. New workspace permissions initially run beside legacy authorization. Module rollout uses explicit modes and can return to legacy behavior without dropping tables.

Database changes are deployed in this order:

1. Workspace permissions and reference data.
2. Shared approval and task infrastructure.
3. Finance core schema and RLS.
4. Finance workflow schema and RLS.
5. Storage core schema and RLS.
6. Storage workflow schema and RLS.
7. Integration, private storage, reporting, and hardening.

## Verification Gates

Every phase requires focused unit tests, direct Supabase/RLS tests, production build, existing access-control tests, and browser verification at desktop and mobile widths in both themes. Finance additionally requires balance and closed-period tests. Storage requires availability, restricted-location, issue/return, and audit-adjustment tests.

No compatibility path is removed until its replacement passes these gates.
